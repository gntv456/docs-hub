## 二、已修复缺陷（11 项 + 1 集成）

### P1 正确性（`299091f`）

1. **集号误判**：`extractEpisodeNo` 把分辨率 `1080`/`720`、年份 `2023` 当成集号 → 电影变「第 1080 集」。
   - 修复：强模式（第N集/SxxExx/E nn/N集）与弱模式（纯数字/行末数字）分离，弱模式命中后排除分辨率与年份噪声；`第1080集` 等明确写法走强模式不受影响。

2. **非短剧分集误判**：纪录片/动漫/综艺（带集号、非 movie/kids 频道）一律判 `short_drama` → 走短剧库检索，命中率低、类型错。
   - 修复：扩大长视频频道清单（`LONG_FORM_CHANNEL_RE`：tv/anime/综艺/纪录片等），有频道上下文的长视频分集不再误判；无频道时仍保留「分集默认短剧」的主场景兼容。

3. **豆瓣反爬标题污染**：详情页反爬时解析出脏标题（如「豆瓣」），覆盖 suggest 接口原本正确的标题。
   - 修复：`parseSubjectHtml` 增加有效性校验——标题缺失/仅站点名且无任何有效字段时返回 `null`，调用方回退 suggest 候选。

### P2 完善度 / 易用性（`299091f` + `ce21719`）

4. **归部纠错**：剧已归错 `series_id` 时，重新刮削无法纠正。
   - 修复：`applyScrape` 新增 `relinkSeries`，开启时丢弃旧 `series_id`、按候选派生 ID 重连同目录兄弟。
   - **隐藏坑**：`apply` 调 `aiAssistParse` 时传入了 `row.series_id`（旧错误 ID），污染 `ai.seriesId`，导致纠错仍用回旧 ID。relink 分支因此改为**直接用候选派生 ID、不信任 `ai.seriesId`**。（写回归测试时发现）

5. **海报去重 + 缓存命中**：无 `series_id` 时海报 key 用 `mediaId`，同部多集同图存多份、重复下载。
   - 修复：keySeed 优先 `series_id`（同部覆盖更新），为空时以 URL 为 key（同图跨集复用）；写入前按 keySeed hash 检查本地缓存，命中直接返回。

6. **清洗误删剧名年份**：`cleanPlayletQuery` 删 `(?:19|20)\d{2}` 误伤剧名（`2030之未来恋人` → `之未来恋人`）。
   - 修复：移除粗暴的年份删除（发布年份对短剧检索影响很小，交由检索源容忍）。

7. **ptang 站点改版零容错**：搜索页去掉「短剧档案」关键词即整体解析失败。
   - 修复：主模板失败时用 `robustTitle` 兜底（链接文本/img alt/h 标签/og:title）。

8. **批量任务风暴式请求**：`targetType:"all"` 逐条串行多源检索，大库下打爆外部源限流。
   - 修复：改为有限并发池（`SCRAPE_JOB_CONCURRENCY = 4`）。

9. **SSRF 收敛**：apply 接口 `candidate.poster` 任意 URL 由后端下载，可探测内网。
   - 修复：`posterCache` 入队前拦截私网/本机地址（`isPrivateHost`：127/10/192.168/172.16/169.254/IPv6 本地/`.local`），既不直接请求也不经第三方代理。与 [media.js](../backend/src/routes/media.js#L55) 的 `isAllowedPosterHost`（对外 302 重定向白名单）互补，分属不同 SSRF 面。

10. **语义/一致性**：`providers=[]` 被当作「全部默认源」（应为「限定无源」）；show/单集置信度阈值不一致（0.5 vs 0.55）；排序 `0.99` 天花板让多源失去区分度。
    - 修复：`providers=[]` 区分 undefined 与空数组；阈值统一 `MIN_CONFIDENCE = 0.55`；排序改用未截断原始分（输出 confidence 上限放宽到 1），`_rankScore` 不泄露。

11. **〔集成〕扫描覆盖已刮削归部/标题**（`ce21719`）：`rebuildSeriesFromDb`/`scanSource` 每次扫描都用路径重算 `series_id`/`episode_no`/`title`，**即便已刮削也覆盖** → apply 写的官方标题被回退、relinkSeries 纠错一扫描就失效。
    - 修复：已刮削（`scraped_at IS NOT NULL`）的媒体保留 apply 的归部与标题，扫描只更新 path/size/mtime/missing；仅未刮削的按路径重算。
    - 这是「单测全绿但集成处崩」的典型，只有跨模块读代码 + 取证才能发现。

## 四、次要发现（评估后未改）

| 项 | 现状 | 不改原因 |
|---|---|---|
| searchAll 失败重试对 TMDB 不生效 | TMDB 并行容错（`p.catch(()=>[])`）吞掉错误 | 是多端点并行容错的合理副作用；各源已有 `fetchWithRetry` 内部重试 |
| apply 给无 series_id 的电影赋 series_id | 文件夹即作品，路径派生 | Emby 式设计，非缺陷 |
| cachePoster 并发下载同图有 race 窗口 | 两个并发都下载、后者覆盖前者 | 幂等不损坏，仅浪费一次请求 |
| 置信度数值在高赛区仍趋同（都到 1.0） | 分数叠加值域天然 >1 | 排序已用原始分解决「顺序退化」；显示值趋同需归一化根治，属较大调整 |

## 五、设计权衡与已知边界

- **「有分号默认短剧」**：无频道信息时，带集号的文件名倾向判 `short_drama`（对齐项目「短剧探索终端」定位）。纪录片/动漫/综艺**必须配长视频频道**（tv/anime/综艺/纪录片等）才能避免误判。
- **series_id 所有权**：apply（用户显式刮削）> 扫描（路径 Emby 规则）。已刮削的归部与标题以 apply 为准；未刮削的由扫描建立。relinkSeries 可强制纠错。
- **TMDB 需配 `TMDB_API_KEY`**，否则安全降级返回空；豆瓣详情页反爬严重，元数据（简介/评分/集数）常拿不到，短剧主源实际是寸光集。
- **批量「全部」任务**：并发 4 + 按 series 去重，但仍会对大量独立剧发起检索；超大库建议分批。

## 六、维护指引

改刮削逻辑时注意：

1. **改 `extractEpisodeNo`**：弱模式（纯数字/行末数字）必须经 `isEpisodeNoise` 过滤；强模式（第N集/SxxExx）不过滤。新增集号写法加到 `strong`。
2. **改 apply 归部**：`seriesId` 优先级是 `row.series_id → ai.seriesId → derivedSeriesId`；relinkSeries 必须绕开 `ai.seriesId`（它带旧 ID 污染）。
3. **改 scanner**：已刮削媒体（`scraped_at IS NOT NULL`）的 `series_id`/`episode_no`/`title` 不能被路径重算覆盖，否则撤销 apply。
4. **加海报源**：若新增图床域名，注意 `posterNormalize.expandPosterCandidates` 的 URL 改写规则；私网拦截在 `posterCache.isPrivateHost`。
5. **加 provider**：失败行为决定是否触发 searchAll 二次重试——`reject` 会进 errors 触发重试，`return []` 不会。
6. **跑验证**：`npm run check && npm run test:unit`（114 项，含 qa-strict 起后端跑 live 网络）。
7. **大规模库性能**（NAS 用户万级以上本地资源）：关键索引 `idx_media_series(series_id, episode_no)`、`idx_interactions_media(media_id)` 不能删——apply 整部同步 / 点赞数查询依赖它们（实测 5万规模 33x、1.2万规模 21x 提速）；`scanSource` / `rebuildSeriesFromDb` 的显式事务（`BEGIN`/`COMMIT`）必须保留（扫描入库 5-6x 提速）。新增高频查询先用 `EXPLAIN QUERY PLAN` 确认走 `SEARCH` 而非 `SCAN`。
