## 1. 问题陈述

三端（Web / Flutter / 后端中间件）各自维护「状态码 → 用户可读文案」映射，后端错误响应存在三层混杂：

| 文案来源 | 数量（api/v1 非测试） | 问题 |
|---|---|---|
| `err.Error()` 直接透传 | ~479 处 | 英文技术黑话直达用户（如 `cannot unmarshal array...`） |
| 中文字符串字面量 | ~84 处 | 与前端 i18n 体系脱节，无法随语言切换 |
| 英文字符串字面量 | ~166 处 | 用户不可读 |

事实信封是 `{"error": string}`（~739 处）。`code` 字段是事后补丁：19 处、8 个码值、**双信封形态并存**（`{"error","code"}` 与 `{"code","message"}` 各占一半），无常量定义、无注册表。

前端已被迫做文本嗅探：`utils/siteError.ts` 按英文关键字子串匹配映射中文；移动端完全不解析 `code`（0 处消费）。`challenge_mode`、`risk_confirmation_required` 等码有跨端语义但只有 1 处 Web 消费。

## 2. 目标与非目标

**目标**
1. 机器可读：每个用户可感知错误携带稳定 `code`，三端可编程分支（如 VIP 引导登录、风险确认弹窗）。
2. 人可读：`message` 为中文默认文案；未来接 i18n 时由前端按 `code` + locale 渲染，后端不再管语言。
3. 兼容：信封收敛为 `{"code": string, "message": string, "error"?: string}`——`error` 保留过渡期（等于 message），老版本前端/移动端零破坏。

**非目标**
- 不一次性翻译 479 处透传错误（技术错误保留原文，仅补 code）。
- 不引入 gRPC/google.golang.org/grpc/status 依赖（纯 REST）。
- 不改成功路径的信封。

## 3. 设计

### 3.1 错误码命名

`<domain>_<reason>` 全小写下划线，与既有 8 个码值风格一致：

```
auth_captcha_failed        site_not_found          downloader_conn_failed
auth_challenge_mode        site_cookie_invalid     download_push_failed
vip_not_verified           site_sync_failed        subscription_limit
admin_required             filter_rule_invalid     transfer_target_invalid
risk_confirmation_required media_metadata_fail     backup_restore_failed
...
```

### 3.2 包结构

```
backend/internal/api/errcode/
  errcode.go      // type Error struct{Code, Message string; HTTP int}; func E(code, msg string, http int) *Error
  codes.go        // 预定义错误值（唯一注册处，禁止 handler 内裸字符串 code）
  errcode_test.go // 唯一性测试：map[code]bool 防重复；HTTP 状态码合法性
```

`Error` 实现 `error`；handler 用 `errcode.Respond(c, err)`——识别 `*errcode.Error`（取 Code/Message/HTTP），否则透传为 `errcode.Internal` + `err.Error()` 进 `error` 字段（日志保留细节，用户只看 message）。

### 3.3 响应信封

```json
// 4xx/5xx
{ "code": "site_cookie_invalid", "message": "站点 Cookie 已失效，请重新登录站点",
  "error": "站点 Cookie 已失效，请重新登录站点" }
```

- `error` 为过渡兼容字段（与 message 同值），计划两个版本后移除。
- 既有 19 处 `{"code","message"}` 信封（auth/guard.go、middleware/auth.go）迁移到统一 helper，码值不变——前端 http.ts 的 403 VIP 白名单零影响。

### 3.4 分层策略（避免一次性 739 处重写）

| 层级 | 改法 | 量 |
|---|---|---|
| L0 基建 | errcode 包 + Respond helper + 既有 19 处 code 统一 | ~20 处 |
| L1 高频用户路径 | auth/login、site CRUD、downloader 测连、订阅、备份恢复的中文/英文 literal 换 errcode 值 | ~80 处 |
| L2 透传收口 | cloud/transfer/plugin 等 `err.Error()` 透传改为 `errcode.Internal` + 归类（如 download_push_failed 保留底层 error 供日志） | 分模块滚动 |

### 3.5 三端对接

- **Web**：`http.ts` 拦截器新增 `err.code = data.code`；业务按需分支（现有 1 处 `risk_confirmation_required` 模式推广）；文案展示继续 `message` 优先。
- **Flutter**：`ApiException` 增加 `code` 字段（`_json()` 解析）；`OpsXxx` 风险确认按 code 分支。
- **后端中间件**：middleware/auth.go 的 `admin_required`/`token_version_mismatch` 改用 errcode 常量。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 老客户端只读 `error` | 过渡期双字段；`error` 弃用前查三端消费点 |
| 码值漂移 | codes.go 唯一注册 + CI 单测查重；新增码必须先进注册表 |
| 中文文案与前端 i18n 重复 | L1 起 message 仅作默认文案，前端 locale 命中 code 后覆盖渲染 |
| 透传错误泄露内部路径 | Respond 对非 errcode 错误统一 Internal 处理，细节进日志不进响应 |
